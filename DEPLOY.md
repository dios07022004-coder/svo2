# Публикация и автодеплой

Репозиторий устроен так, что **его содержимое — это и есть корень сайта**:
`index.html` лежит в корне, рядом `assets/`, `robots.txt`, `sitemap.xml`.
Поэтому на хостинге репозиторий клонируется прямо в каталог сайта, без вложенных папок.

```
GitHub (main)  ──push──►  GitHub Actions  ──ssh──►  reg.ru: git reset --hard
```

---

## Шаг 1. Ключ для деплоя

Ключ нужен, чтобы GitHub мог зайти на хостинг без пароля.
Свой личный ключ использовать не стоит — заведите отдельный.

**На своём компьютере:**

```bash
ssh-keygen -t ed25519 -C "github-deploy-svo2" -f ~/.ssh/regru_deploy -N ""
```

Получится два файла:

* `~/.ssh/regru_deploy` — приватный, пойдёт в секреты GitHub;
* `~/.ssh/regru_deploy.pub` — публичный, пойдёт на хостинг.

**Публичный ключ на хостинг.** Подключитесь по SSH (данные — в ISPmanager,
раздел «Пользователи» → ваш логин) и выполните:

```bash
mkdir -p ~/.ssh && chmod 700 ~/.ssh
echo "ВСТАВЬТЕ_СЮДА_СОДЕРЖИМОЕ_regru_deploy.pub" >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
```

Проверка с компьютера — должно пустить без пароля:

```bash
ssh -i ~/.ssh/regru_deploy ВАШ_ЛОГИН@server233.hosting.reg.ru
```

---

## Шаг 2. Первичный клон на хостинге

Один раз вручную. Подключитесь по SSH и выполните:

```bash
# Путь к корню сайта смотрите в ISPmanager → Сайты → колонка «Корневая директория»
cd /home/ВАШ_ЛОГИН/ВАШ_ДОМЕН/www

# Каталог должен быть пустым. Если там лежит заглушка хостера — уберите её:
ls -la
rm -f index.html index.php

# Системный git на reg.ru — версии 1.7.1 и не дружит с современным TLS.
# Если доступен git2192 — используйте его.
git2192 clone https://github.com/dios07022004-coder/svo2.git .
# либо, если алиаса нет:
# git clone https://github.com/dios07022004-coder/svo2.git .
```

Точка в конце обязательна — иначе появится лишняя вложенная папка `svo2`.

Откройте сайт в браузере: должна открыться главная страница.

## Шаг 3. Секреты в GitHub

`Settings` → `Secrets and variables` → `Actions` → `New repository secret`.

| Имя | Значение |
|---|---|
| `REGRU_HOST` | `server233.hosting.reg.ru` |
| `REGRU_USER` | логин хостинга (вида `uXXXXXX`) |
| `REGRU_PATH` | `/home/uXXXXXX/ВАШ_ДОМЕН/www` |
| `REGRU_SSH_KEY` | содержимое `~/.ssh/regru_deploy` целиком, вместе со строками `-----BEGIN…` и `-----END…` |
| `REGRU_PORT` | только если SSH висит не на 22 |

Приватный ключ копируйте так:

```bash
cat ~/.ssh/regru_deploy | pbcopy
```

## Шаг 4. Проверка

```bash
git commit --allow-empty -m "Проверка автодеплоя"
git push
```

Вкладка `Actions` в репозитории → должен появиться зелёный запуск
«Deploy to reg.ru». В логе последнего шага будет видно, какой коммит выкачен.

Дальше всё автоматически: любой `git push` в `main` обновляет сайт за ~20 секунд.
Запустить вручную можно из вкладки `Actions` → `Deploy to reg.ru` → `Run workflow`.

---

## Запасной вариант: без секретов в GitHub

Если не хотите класть SSH-ключ в GitHub, хостинг может забирать обновления сам.
В ISPmanager → «Планировщик (cron)» добавьте задание раз в 5 минут:

```
*/5 * * * * cd /home/ВАШ_ЛОГИН/ВАШ_ДОМЕН/www && git2192 fetch origin main && git2192 reset --hard origin/main >/dev/null 2>&1
```

Минус — обновление приходит с задержкой до пяти минут. Плюс — никаких
ключей за пределами хостинга. Оба способа можно совмещать: workflow даёт
мгновенный деплой, cron подстраховывает.

## Повседневная работа

```bash
git add -A
git commit -m "Что изменил"
git push
```

Правки контента — это обычные файлы в `assets/js/data/`, отдельная сборка не нужна.

---

## Что не попадает в репозиторий

Смотрите `.gitignore`. Намеренно исключены папки `фото для наполнения/`
и `картинке для операторов/`: они весят больше 11 МБ, на сайте не используются
(там оптимизированные копии в `assets/img/`), а при клоне в корень сайта
стали бы доступны по прямой ссылке. Среди них есть сток с водяными знаками
и фотографии реальных людей — публиковать их нельзя.

Оригиналы остаются у вас локально. Если нужен их бэкап — заведите отдельный
приватный репозиторий или облачное хранилище.

## Про вебхук приёма заявок

Адрес вебхука лежит в `assets/js/config.js` и попадает в репозиторий.
Это не утечка: файл всё равно отдаётся браузеру каждого посетителя, так что
адрес виден любому, кто откроет исходники страницы. Но раз он публичный —
на стороне n8n имеет смысл поставить ограничение частоты запросов и проверку
данных, иначе в CRM можно накидать мусорных заявок.
